Data Flow Bible

How data moves between our applications, the central database, the data lake and the dashboards. Every design, pull request and vendor integration follows this page. If something needs to break a rule, the team changes the page first.

Write

Every app writes to one PostgreSQL database.

Read

The data lake reads only from that database.

See

People see only what their role, scope and clearance allow.

One record, end to end

An assistant professor in the CSE department punches in at the Block A biometric device. Times match the proposed freshness targets.

09:02:10

The device posts the punch to the integration gateway with its device key. The gateway checks the key, drops a duplicate punch sent 3 seconds later (same idempotency key) and writes one row to the HRMS punch table in the hrms schema.

09:02:11

The row reaches the read replica. Nobody else has touched the primary.

09:03

CDC reads the change from the replica. The table is on the allow-list, so the change goes to Bronze as an exact copy.

09:10

Silver types and de-duplicates the row and replaces the employee id with a stable lake token. No name or phone number exists in the lake.

09:15

Gold refreshes "staff attendance by department, by day".

09:20

The HoD of CSE opens the dashboard. The role gate lets them see it. The scope gate limits it to CSE. The mask gate hides salary. To see who is late, they click a row. The Intranet resolves the token, checks the HoD's permission on that person and writes pii_access_log.

Golden rules

Cite them by number in design reviews and pull requests ("breaks rule 6"). Rules marked in red are hard stops.

  1. One owner per record

    Each kind of record has exactly one system that creates and changes it (see Who owns what). Every other system reads it.

  2. In-house apps connect directly

    Intranet, HRMS and CourseAI use the central PostgreSQL. Each has its own schema and its own database role, with only the grants it needs.

  3. An app writes only its own schema hard stop

    To change another app's data, call that app's API or raise a wf approval. Reading across schemas goes through views and grants.

  4. Outside systems never touch the database hard stop

    Devices, Google / MS 365, the LMS and the University CRM post to the integration gateway. The gateway authenticates the source, validates and de-duplicates, then writes into the owning schema.

  5. One shared foundation

    People, org units, accounts, roles, approvals, consent and audit exist once (org, people, iam, authz, wf, privacy, audit). No app keeps its own copy of a person, a department or a role.

  6. The lake reads only from the central database hard stop

    Through CDC from the read replica, never the primary. Nothing writes into the lake directly: no app, device, vendor or spreadsheet upload. Data from outside lands in the database first.

  7. Personal data stays home hard stop

    pii, iam, privacy, audit, names and the confidential tables are not published to CDC. In the lake, a person is a token.

  8. Dashboards never query the live database hard stop

    They read Gold through the analytics API. If the lake is late, the dashboard says so. It does not fall back to the live database.

  9. Every read passes the RBAC layer

    Role, then scope, then mask, on every query. Nobody gets raw SQL on the lake. Analysts get a scoped, masked role like everyone else.

  10. Roles are defined once, in authz

    The lake and the dashboards use the same roles, permissions and org scopes as the apps. There is no second permission list to keep in step.

  11. Numbers come from the lake, names come from the app

    A dashboard shows counts, rates and tokens. Opening a named person goes back to the Intranet, which checks the permission and logs the access.

  12. The lake is read-only for actions

    Flagging a student, raising a ticket or starting an approval goes through the app's API, which writes the central database. A lake job never writes back.

  13. A schema change is a contract change

    A new or renamed column updates the data dictionary, privacy.data_element and the CDC allow-list in the same change. CDC drops columns it does not know until they are registered.

  14. No hard-coded policy

    Freshness targets, masking rules, the small-number threshold and retention windows are rows an administrator can edit. They are never constants in code.

Access: role, scope, mask

The RBAC layer sits between Gold and every dashboard. It runs three checks in order. Each check reads the same authz tables the apps use.

1 · Role

Which dashboards and metrics you can open at all. A permission such as analytics.staff_attendance.view is granted to a role.

Source: authz.role_permission, authz.account_role

2 · Scope

Which rows you see. A grant scoped to the School of Engineering with descendants covers every department under it. A global grant covers the university.

Source: account_role.scope_org_unit_id, include_descendants

3 · Mask

Which columns show in clear. Salary, individual marks and tokens are masked, banded or hidden unless your role is cleared for them. Every unmasked view is logged.

Source: mask-rule rows (column × permission), edited by the DPO

Groups smaller than the small-number threshold (proposed: 5 people) show "<5" instead of a count, so nobody can be singled out of a small class or department. Role and scope changes take effect within 60 seconds, because the RBAC layer checks the live authz tables, not the lake's copy.

Personal data (DPDP Act 2023)

The university is the data fiduciary for every student, employee and guardian. The lake inherits the controls already built into the database. It does not invent new ones.

Stays out of the lake

The pii, iam, privacy and audit schemas, names in people.person, and confidential tables (feedback responses, disciplinary cases, breaks in study, ticket text, answer scripts). The CDC allow-list matches the existing intranet_analytics grants.

People become tokens

Silver replaces each person id with a keyed hash. The key sits in the KMS, not the lake. Only the Intranet can turn a token back into a person, and it logs each lookup in privacy.pii_access_log.

Masked by role

Salary, individual marks and CGPA, attendance per person and leave reasons are masked, banded or hidden unless the role is cleared (gate 3).

Erasure reaches the lake

When privacy.erasure_log records a DELETE or ANONYMISE, CDC carries it to Bronze, Silver and Gold. Bronze history is kept only for a set window, so old copies age out too.

Consent withdrawn means excluded

Marts built on consent-based purposes drop a person as soon as privacy.v_active_consent no longer lists them.

Children (under 18)

No tracking or behavioural monitoring of minors (§9(3)). CourseAI activity for under-18 students is reported as counts only. Whether learning analytics may cover minors at all is a DPO decision.
